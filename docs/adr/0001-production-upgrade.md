## 一、背景

揽乐当前状态是「功能完整、单机可用」，但距离「可维护、可观测、可回滚、可审计」的生产级要求仍有系统性差距。评估结论详见
[`PRODUCTION-UPGRADE.md` 第二节](../architecture/PRODUCTION-UPGRADE.md#二现状评估)，要点如下：

| 维度 | 现状事实 | 生产级差距 |
|---|---|---|
| 类型体系 | 全 JS，无 `typecheck` 门禁 | 核心域缺少类型约束，重构回归只能靠测试兜底 |
| IPC 契约 | `src/shared/ipcContract.js` 约 26KB、111 个 METHODS，纯手写 | 类型、实现、文档三处可能漂移 |
| 主进程结构 | 入口 `index.js` 与下载引擎 `downloadQueue.js` 偏大，编排与业务混杂 | 领域边界不清，单文件不可控 |
| 测试 | 380+ `node:test` 文件，但含大量源码 grep 断言，E2E 为 0 | 行为覆盖不足，重构即红 |
| 发布 | tag → 草稿 Release，仅 Windows，无证书 | 无签名、无灰度、无回滚演练 |
| 可观测 | 文件日志 + diagnose + redact | 无崩溃转储、无启动/播放指标、无诊断包 |

已有优势必须保留、不重做：契约派生白名单、参数钳制、启动覆盖对账、MCP 同源、SSRF/路径沙箱、Cookie 安全存储、原子写、下载终态立即落盘、CI 归因脚本。

触发本决策的直接问题：**结构性技术债已开始以「修复成本递增」的方式影响发布节奏**——契约与实现漂移、测试不稳定、发布无信任链，三者互相放大。

## 二、决策

**采用 [`docs/architecture/PRODUCTION-UPGRADE.md`](../architecture/PRODUCTION-UPGRADE.md) 作为未来 18 周的唯一升级基线**，按 4 个里程碑推进，不追求一次性重写，采用「双轨演进 + 每周可发布」。

### 2.1 总体节奏

- **周期**：18 周，4 个里程碑（M0 基线治理 2 周 → M1 架构与类型 6 周 → M2 质量与发布 6 周 → M3 性能与验收 4 周）。
- **里程碑出口**：每个里程碑必须满足方案第八节列出的验收条件才可进入下一阶段；未达标则顺延，不并行抢跑。
- **发布节奏**：双轨期内保持每周可发布；不允许长期「重构分支冻结」。

### 2.2 三条主线

| 主线 | 决策要点 | 里程碑归属 |
|---|---|---|
| **架构收敛** | 主进程按 `bootstrap / ipc / domain / infra / platforms / mcp` 分层，`domain` 禁止 import `electron`；下载引擎拆分为 `engine / queue / persist / transfer`；共享契约成为唯一事实源；旧渲染层限期删除 | M1、M3 |
| **质量工程** | 渐进 TypeScript（先 `src/shared` 全部 8 个文件、再 `src/main/domain`，`allowJs` 起步、strict 逐步收紧）；行为测试金字塔（单元 70% / 集成 20% / E2E 10%）；**禁止新增源码 grep 断言**，存量冻结并逐批替换；CI 增加 `typecheck`、覆盖率与 E2E | M0、M1、M2 |
| **发布与信任** | 代码签名 + 时间戳 + 更新包签名校验；草稿 Release + sha256 产物清单；灰度发布（延迟 `latest.yml` 更新，观察 24h）；保留上一版安装包与 `latest.yml` 以支持一键回滚；结构化日志 + 崩溃转储 + 诊断包 | M2、M3 |

### 2.3 三项关键工程决策（本 ADR 直接约束）

1. **渐进 TS，不做大爆炸迁移**
   - M0 建立 `tsconfig`（`allowJs` + `checkJs`）与 CI typecheck，覆盖 `src/shared` **全部 8 个文件**；`vue-tsc` 推迟到 M1 渲染层 TS 迁移时引入。
   - 复验结果（2026-11-07 第二次验收）：`tsconfig` 的 `include` 为 `src/shared/**/*.js`，覆盖**全部 8 个文件**，**已验证**；CI Typecheck 步骤已接入并**本地实跑通过**（远程 CI 首次 PR 待确认）；未引入 `vue-tsc`，本文不宣称已使用。
   - 迁移顺序固定：`src/shared`（契约、DTO、错误码）→ `src/main/domain` → `src/renderer/app`。
   - 每阶段收紧 `strict` 开关，禁止为过门禁而堆 `any` / `@ts-ignore`（必须带理由与到期日）。

2. **契约 schema 化，生成物不手写**
   - `channels / schema / methods / events` 以 schema（zod）为单一事实源。
   - 由脚本生成：preload 白名单、渲染层 `bridge` 类型、MCP 工具清单、契约文档、契约测试。
   - 契约变更必须先改 schema 并重新生成，禁止直接改生成物。

3. **签名与灰度是发布前置条件，不是可选项**
   - 采购 Windows OV/EV 证书，CI 通过 `CSC_LINK` / `CSC_KEY_PASSWORD` 注入；`verifyUpdateCodeSignature` 从「空转」变为真实校验。
   - 发布采用草稿 Release，先上产物与哈希、延迟 `latest.yml`，观察 24h 再放开更新。
   - 回滚能力：至少保留上一版安装包与 `latest.yml`，回滚脚本可一键执行，且每季度演练一次。

### 2.4 明确不做

- 不新增源码 grep 断言（存量只减不增）。
- 不在同一 PR 内同时做「结构迁移 + 功能新增」。
- 不为赶进度跳过里程碑出口判据。
- 不在无签名证书的情况下对外宣称「可自动更新」。

完整目标架构、测试金字塔、安全清单、性能预算、风险登记见
[`PRODUCTION-UPGRADE.md`](../architecture/PRODUCTION-UPGRADE.md)。

## 三、备选方案

| 方案 | 描述 | 结论 | 理由 |
|---|---|---|---|
| A. 一次性重写 | 冻结功能，重建主进程与渲染层后切换 | **否决** | 交付中断 3 个月以上；回归面无法估计；团队规模不足以支撑并行维护两套系统 |
| B. 只做局部修补 | 仅补测试 + 补签名，不动结构 | **否决** | 结构债不还，契约漂移与单文件膨胀继续恶化；签名只能解决「信任」一项 |
| C. 先全量 TS 再谈架构 | 先把全仓库迁 TS，再分层 | **否决** | 在待拆分的旧结构上固化类型，返工量翻倍；迁移成本先于收益出现 |
| D. 维持现状 + 加强人工验收 | 不投入工程改造 | **否决** | 发布风险不可控（无签名、无回滚）；缺陷定位成本持续上升 |
| E. 18 周三主线渐进方案（**本决策**） | 双轨演进，每周可发布，里程碑设硬出口 | **采纳** | 风险可分批消化；每阶段都有可验证产出；与现有 CI / 测试资产可衔接 |

选择 E 的关键权衡：**牺牲短期功能速度，换取可回滚与可审计**；以里程碑出口而非日期作为推进条件。

## 四、后果

### 4.1 正面

- 每 2–6 周都有可验证的结构性收益（typecheck 可运行、契约生成、签名产物、E2E 绿灯）。
- 契约漂移从「靠人对账」变为「生成 + 自动断言」。
- 发布从「手工上传」变为「可灰度、可回滚、有哈希与签名」。
- 重大决策有 ADR 留痕，后续维护者可追溯「为什么这么改」。

### 4.2 负面 / 成本

- **投入**：约 45–55 人周（含 20% 缓冲），架构/主进程 1.0 FTE、渲染/类型 1.0 FTE、质量/发布 0.5–1.0 FTE。
- **双轨复杂度**：旧渲染层保留期间，构建与测试需要同时照顾两层，短期维护成本上升。
- **门禁变严**：`typecheck`、覆盖率、契约测试会延长 PR 反馈时间（目标 ≤10 分钟，需分片与缓存控制）。
- **证书周期**：OV/EV 证书采购需 1–3 周，若 M0 未启动采购，将卡住 M2 签名验收。

### 4.3 风险与缓解（摘要）

| 风险 | 缓解 |
|---|---|
| 全量测试不稳定 | M0 先治理：`--test-timeout` + 分片 + flaky 隔离到 `test/quarantine/`，两周内修复或删除 |
| TS 迁移拖慢交付 | 渐进 strict，先 `shared` 后 `domain`；禁止 `any` 堆积 |
| 重构期间功能冲突 | 双轨 + 每周集成 + 特性开关；结构迁移与功能新增分 PR |
| 旧层删除引发回归 | 删除前置条件：新层 E2E 全绿 2 周、崩溃率不高于旧层、回退请求为 0 |
| 签名证书未按时到位 | M0 即发起采购；未到位前签名与灰度项保持「未验证」，不得对外宣称自动更新可用 |
